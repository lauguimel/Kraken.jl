# Viscoelastic bugs — 2026-05-01

## Verdict

The previous `R=30`, `Wi_R=0.1` agreement is a single-point crossing, not a
solver validation. The current branch should be treated as **not validated**
for production viscoelastic cylinder use until the force/coupling bugs below
are fixed.

## Confirmed bugs

### B0 — Single-point validation is invalid

Evidence:

- `bench/viscoelastic_audit/AUDIT_WI_SWEEP_20260430.md` shows that Kraken and
  rheoTool agree near `Wi_R=0.1` but have different `Cd(Wi)` slopes.
- Kraken with the previously accepted mode gives:
  - `Wi=0.05`: `Cd=149.76` vs rheoTool `131.81`.
  - `Wi=0.10`: `Cd=130.74` vs rheoTool `130.43`.
  - `Wi=0.20`: `Cd=111.74` vs rheoTool `126.83`.

Impact: `VALIDATION_R30_OLDROYDB.md` remains a numerical record for one point,
but it is not a valid solver-level validation.

### B1 — `source_scaled_mea` is a cancellation, not a force law

Evidence:

- The default validated mode applies CE-amplified stress in the dynamics and
  then rescales only the post-source MEA boundary increment.
- Local canary runs at `Wi_R=0.001` fail the Newtonian-limit check:
  - `R=8`, CE/scaled: `Cd_VE/Cd_Newt ≈ 1.99`.
  - `R=12`, CE/scaled: `Cd_VE/Cd_Newt ≈ 1.83`.
  - Liu-direct/post-source on the same short runs is much closer:
    `0.94–0.96`.
- `test/test_viscoelastic_force_accounting.jl` already marks the post-source
  MEA analytic-stress equality as broken: the measured impulse is not a
  physical surface traction.

Impact: `drag_mode=:source_scaled_mea` must not be used as a validation default.
It can remain only as a diagnostic until a correct total-force formula is
derived.

### B2 — `compute_polymeric_drag_2d` is not a curved-surface quadrature

Evidence:

- `test/test_polymeric_drag_geometry.jl` uses the exact analytic case
  `τ_xx = x-cx`, where `Fx = πR²`.
- Current helper gives ratios around `3.1` at `R=20–40`.

Impact: `Cd_p` and `Cd_split_explicit` are diagnostics only. They must not be
used as physical polymeric drag until replaced by a `q_wall`-aware surface
quadrature.

### B3 — `hpc/sweep_wi_cylinder.jl` ignored `KRAKEN_GEOMETRY_MODE`

Evidence:

- The script parsed `geometry_mode` but always used
  `Nx=30R`, `Ny=4R`, `cx=15R`, `cy=(Ny-1)/2`.

Impact: geometry sweeps could be mislabeled. This file now uses the same
`cylinder_geometry` helper as `hpc/force_scheme_matrix.jl`.

### B4 — 4:1 contraction log-conformation inlet used `C` instead of `Ψ=log(C)`

Evidence:

- The contraction isolation matrix at `H_out=8`, `Re=1`, `Wi=0.1` showed
  direct conformation with `max_trace_C ≈ 2.016`, but log-conformation with
  `max_trace_C ≈ 5.439`.
- The value is diagnostic: `5.4` is close to `2e`, consistent with injecting
  equilibrium `C_xx≈1`, `C_yy≈1` into a field interpreted as `Ψ`, then
  reconstructing `C=exp(Ψ)`.
- The cylinder driver already converted the analytical inlet profile to
  `log(C)` for log-conformation; the contraction driver did not.

Impact: any previous contraction/log-conformation result is invalid. This is a
pre-`Cd` bug and confirms the need for step-geometry isolation before obstacle
drag validation.

Status: fixed in `src/drivers/contraction_libb.jl` and covered by
`test/test_contraction_libb.jl`. The post-fix Metal canary gives
`max_trace_C ≈ 2.016` for direct conformation and `≈ 2.010` for
log-conformation on the same `H_out=8`, `Re=1`, `Wi=0.1` run.

### B5 — Contraction `X_R` post-processing used an exact corner sign

Evidence:

- In the `H_out=8`, `Re=1`, `Wi=0.05` contraction matrix, fields remained
  symmetric (`ux_sym`, `uy_asym` around `1e-4` relative), but
  `vortex_length_contraction_2d` returned asymmetric values such as
  `X_R_s/H=3.875`, `X_R_n/H=0`.
- The helper used `sign(ux[i_step-1, j_probe])` at the single corner-adjacent
  cell. On Float32/GPU runs this sample can be exactly zero or noise-dominated.

Impact: contraction `X_R` was not a reliable diagnostic for short/low-Wi runs.
The stress and symmetry fields were still useful; the scalar vortex length was
not.

Status: fixed by using a velocity tolerance, skipping zero/noisy corner
samples, and treating positive near-corner velocity as no detected vortex.
Covered by `test/test_contraction_libb.jl`.

### B6 — Step geometries need masked inlet/outlet BCs

Evidence:

- The 4:1 contraction has a partial downstream outlet: only
  `j_low ≤ j ≤ j_high` is fluid at `i=Nx`.
- The original default `BCSpec2D` applied `ZouHePressure` on the whole east
  face, including solid blocks above and below the outlet.
- The same infrastructure problem blocks a clean backward-facing-step case,
  where the west inlet is also only partially fluid.

Impact: step cases could mix rheology errors with inlet/outlet reconstruction
errors. This is a pre-obstacle issue and must be fixed before using BFS as a
diagnostic.

Status: added `MaskedZouHeVelocity` and `MaskedZouHePressure`, plus masked
conformation inlet/outlet resets. Step cases now use `StepChannelGeometry2D`
specs and the shared `run_conformation_step_libb_2d` pipeline; the contraction
entry point is only a compatibility wrapper. The step-isolation sweep now runs
`KRAKEN_GEOMETRIES=contraction,bfs` through that shared pipeline.

## High-probability bugs to isolate next

### S1 — Log-conformation wall BC applies CNEBB to `Ψ`, not `C`

CNEBB is a conservative boundary reconstruction for conformation components
`C`. The log-conformation driver currently applies the same population
boundary treatment to `Ψ = log(C)`. That is only approximately equivalent at
low deformation.

Expected failure mode: correct-looking low-Wi/local tests, wrong `Cd(Wi)` slope
near the cylinder.

Next test: compare direct-C and log-C with the same force mode and a
wall-local diagnostic that converts `Ψ → C`, applies a C-based wall condition,
then maps back to `Ψ`.

### S2 — CNEBB equilibrium velocity convention is inconsistent

The CNEBB comments still describe `u_wall = 0`, while the production wrapper
uses the local hydrodynamic velocity at the boundary fluid node. One of these
conventions is wrong for the intended Liu comparison.

Next test: expose a driver option for zero wall velocity vs local velocity and
run the Wi sweep.

### S3 — Hermite source prefactor convention is not settled

The branch contains three effective conventions:

- standalone post-collision CE-corrected source,
- Liu-direct source,
- integrated collision source.

The latest sweep shows post-collision and integrated timing are not the main
issue, but the code still needs one documented default. Until the total force
accounting is fixed, changing this prefactor can only move errors around.

## Immediate engineering decision

Do not claim the viscoelastic cylinder solver is validated from the `Wi_R=0.1`
point alone.

The next useful work is not another Cd calibration. It is:

1. Replace/disable `source_scaled_mea` as a validation path.
2. Implement a physical `q_wall`-aware polymer traction quadrature.
3. Isolate CNEBB-on-`Ψ` vs CNEBB-on-`C`.
4. Re-run the Wi sweep against rheoTool.
